# 前端测试与验收

本仓库当前只有 `dev`、`build`、`preview` 三个 npm 脚本。没有 `test`、`lint` 或类型检查脚本，也没有可直接运行的项目测试目录。不要记录不存在的测试命令或沿用旧工作区的测试结果。

## 命令检查

在前端仓库根目录执行：

```bash
npm ci
npm run build
```

`npm ci` 按锁文件安装依赖，`npm run build` 检查生产构建并生成 `dist/`。构建通过不能证明接口、页面流程或部署通过。

查看构建页面：

```bash
npm run preview
```

业务联调使用 `npm run dev`。本地 `/api` 由 Vite 代理到 `http://127.0.0.1:8080`，生产转发由 Nginx 配置。不要把 preview 页面能打开当成生产环境已验收。

## 联调准备

- 按[开发说明](DEVELOPMENT.md)先启动后端中间件，再启动后端和前端。
- 记录前后端提交、Node/npm 版本、浏览器、测试环境和测试时间。
- 准备测试账号、可访问图片、普通商品和活动时间内的抢购商品。不假定固定商品 ID 或固定库存。
- 保留浏览器存储以验证恢复场景。只在无待确认购买时清理测试数据；切换账号后重新核对当前会话。
- 打开 Network 和 Console。核对请求方法、ID、响应码及响应内容，截图和日志须脱敏。

后端验收另见[后端测试说明](https://github.com/CLPS-BLAKE/tikcookie-api/blob/main/docs/TESTING.md)。本地前端检查不替代后端状态、库存或中间件验证。

## 抢购与支付专项

1. 从首页真实抢购商品进入详情。确认个人额度加载；达到上限时不发新购买请求。另覆盖“已有原购买记录且额度已满”：详情页“继续本次购买”同样被限购检查阻止，无法进入原购买进度。用原账号通过已打开的购买进度页、原进度链接或“我的订单”查询原结果，确认没有生成新请求键或新购买。我的订单暂未查到时，不将其判为原请求失败。
2. 提交前保存请求键；确认进入进度页不被当作建单成功。查询到真实订单后才进入支付。
3. 模拟刷新、断网、响应丢失。使用原请求继续购买，核对请求键不变，不自动创建第二次购买。
4. 等自动查询截止后，确认停止不等于失败。通过手动查询和我的订单确认原结果。
5. 仅在明确要再买时使用新请求。验证二次确认，并记录原请求仍可能成单的风险。
6. 核对支付页订单号、金额、状态和 `payDeadline`。刷新不重置期限，过期不能继续支付。
7. 支付响应丢失时先刷新订单，不凭网络错误判失败或跳成功。待支付取消后重新查询状态。
8. 同一浏览器切换账号、退出后重登、禁止本地存储时，确认不会误用别人的购买记录或继续发出旧会话操作。
9. 去使用和退款后的真实状态需通过订单重新查询。库存和额度变化由后端验证，不从前端提示推断。

取消、退款、限购和后台任务的规则以[需求文档](https://github.com/CLPS-BLAKE/tikcookie-api/blob/main/docs/需求文档.md)及[接口文档](https://github.com/CLPS-BLAKE/tikcookie-api/blob/main/docs/接口文档.md)为准。支付、退款均为教学模拟，不验证真实资金流。

## 文档与证据

文档变更应检查相对链接、图片引用和页内锚点。删除文档后搜索旧文件名，确认保留文档和模板没有悬空导航。后端链接必须指向 main 主线文档；未访问验证的外链应明确记录。

PR 或检查报告分别写明：

- 执行命令、退出码、构建告警。
- 实际验证的路由、操作、接口结果和脱敏截图。
- 未验证项、阻塞原因和风险。

没有后端、没有浏览器检查或接口不可用时，写“未验证”及原因，不写“全链路通过”。不把模拟提示、本地缓存或构建通过替代真实验收。
