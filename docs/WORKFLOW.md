# 开发、评审与合并流程

## 1. 标准流程

1. 建立任务，写明负责人、范围、验收方式和关联仓库。
2. 开发者同步 `main`，创建短期任务分支。
3. 完成功能和本地验证，推送分支。
4. 创建 Pull Request，按模板填写全部适用内容。
5. 自动检查执行代码检查、测试和构建。
6. 评审者检查实现、接口影响、验证证据和配置变化。
7. 作者处理意见并重新验证。
8. 满足合并条件后，由代码管理员执行 Squash merge。
9. 删除已合并分支，并在任务中记录结果。

## 2. 合并条件

- 至少 1 名合格评审者批准。
- 新提交应使旧批准失效。
- 所有评审讨论已解决。
- 必需 CI 检查通过。
- 分支已处理与 `main` 的冲突。
- 接口或环境变量变化已经更新文档。
- 页面变化具有截图、录屏或可复现验证说明。

## 3. PR 范围

一个 PR 应解决一个清晰目标。建议控制为可在一次评审中理解和验证的规模。大型功能拆分为骨架、核心流程、异常处理和测试等连续 PR。

## 4. 前后端协作

接口变化在实现前写入 [API_CONTRACT.md](API_CONTRACT.md) 或关联接口文档。破坏兼容性的修改必须说明：

- 前端与后端合并顺序
- 是否需要临时兼容旧字段
- 联调负责人和验证场景
- 发布与回退方式

## 5. 管理员自己的修改

代码管理员自己的 PR 也必须经过流程，并由另一名拥有仓库 Write 权限的成员审核，避免自写、自审、自合并。
